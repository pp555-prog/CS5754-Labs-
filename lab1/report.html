1. Implementation

All kernels are deliberately naive, compiled exactly as the provided Makefile does (gcc, no -O flag, i.e. -O0), to serve as the baseline for later labs. Every multi-dimensional array uses the provided pointer-to-pointer layout with each row allocated separately, because callers free outputs row by row.

  • convolution(): stride 1, no padding, output side inputSize − kernelSize + 1. Six nested loops (filter, out-row, out-col, channel, kernel-row, kernel-col); the accumulator is reset per output cell, the filter's bias is added once after summing over all channels, then relu() is applied.
  • relu(): x > 0 ? x : 0 on a scalar (applyRelu() is the provided array wrapper).
  • linear(): out[j] = b[j] + Σi in[i]·W[j][i]. The weights are indexed [output][input] and include a bias, as the provided tests require (the primer's W[i][j], bias-free form does not match the code). No activation inside.
  • matmul(): returns NULL if A_cols ≠ B_rows; otherwise the textbook i-j-k loop with a scalar accumulator.
  • softmax(): three passes: find the max, sum expf(x − max), then write (x − max) − logf(sum). This is log-softmax: the stub's comment says "normalise and apply log" and the provided test checks Σ exp(out) = 1. Subtracting the max prevents overflow.
  • Also implemented (needed by the provided tests): flatten() (channel-major) and predict() (argmax, first index wins ties).

2. Unit tests

All 26 tests pass (make all_tests): the 11 provided plus 15 new ones. Expected values were computed by hand.

  • test_conv.c (5 new). The provided helpers only build 5×5 single-channel images and 1-channel 3×3 kernels, so I added helpers that build tensors of any shape from flat arrays. Cases: (1) the handout's 2-channel 4×4 example with a 2×2 filter and bias 2 (all nine outputs, 36…156), which checks cross-channel summation and a single bias add; (2) negative weights so ReLU must clip outputs to 0 while a positive one survives; (3) three filters with different biases (output depth, per-filter bias, ReLU on one filter only); (4) a 1×1 kernel over 2 channels; (5) a kernel the size of the image (1×1 output, boundary indexing).
  • test_linear.c (4 new): the primer's example rewritten for the [out][in] layout; identity weights (output = input); negative inputs, weights and biases (checks that no ReLU is applied); and 4 inputs → 1 output (non-square).
  • test_matrix_ops.c (6 new): the primer's 2×2 example; a non-square (2×3)(3×2) product; A·I = A; a (1×4)(4×1) dot product; a (2×1)(1×3) outer product (output larger than both inputs, catches M/N/K mix-ups); and a second incompatible shape (3×2)(3×2) that must return NULL.

3. Profiling methodology

Harness. perf/profile.c takes <kernel> <size> <iters>, builds random inputs in [−1, 1] once (fixed seed, so every trial sees identical data), then calls the kernel iters times, freeing each output (the allocation is part of the function). Iteration counts were calibrated so each run spends ≈8.6–11 s inside the kernel loop. To quantify the code outside the kernel, I timed every large configuration with iters = 0: setup takes 0.009–0.37 s, i.e. ≤ 3.5 % of a run (worst case linear 4096², which initialises 16 M random weights); for small configurations it is negligible. Setup-only runs were also profiled and look nothing like the kernels (e.g. relu 10³ setup: 29.5 % Frontend Bound vs. 1.4 % for the kernel), so without the repetition loop they would have distorted the results.

Measurement. Each run is a separate SLURM job on the ece5755 node (Xeon Silver 4514Y, Sapphire Rapids; 48 KB L1d and 2 MB L2 per core, 30 MB L3 per socket), pinned to one core: toplev.py --core S0-C0 -l1|-l2 -v --no-desc --force-cpu spr taskset -c 0 ./perf/profile … (perf/run_toplev.sh). Each of 15 configurations (5 kernels × 3 sizes spanning L1/L2-resident to larger than the 30 MB L3) was run 3 times at level 1 and 3 times at level 2, and perf/summarize.py averages the trials. Every run reported MUX = 100 % (no counter multiplexing). Results are very repeatable: the standard deviation across trials is ≤ 0.4 percentage points for 13 of 15 configurations and 3.2 points in the worst case (softmax 10⁵), and the mean time per call of the level-1 and level-2 run sets differs by ≤ 1.6 %. The relu harness writes relu(in[i]) into a separate output array instead of calling the in-place applyRelu(); otherwise every iteration after the first would see only non-negative inputs and the branch behaviour (below) would disappear.

5. Analysis: where the bottlenecks are and why

relu: branch-bound, not memory-bound. At -O0 the ternary compiles to a conditional branch, and with random-signed inputs that branch is a coin flip. For 10⁵ and 10⁷ elements ~60 % of slots are Bad Speculation, almost all Branch Mispredicts (Fig. 2), and Frontend Bound rises to 15 % largely Fetch Latency (8.3 %), consistent with the front end being re-steered after every misprediction. The 10³ case is the surprise: 71 % Retiring and 2 % Bad Speculation, and 3.8× faster per element. Because the same 1 000-element sign pattern repeats every call, the history-based branch predictor learns it; 10⁵ outcomes are far beyond what it can memorise. Despite the 80 MB working set at 10⁷, Memory Bound stays below 1 %: at ~11 ns per element the loop needs only ≈0.7 GB/s of sequential, prefetch-friendly traffic. The primer's starting hypothesis ("leans memory-bound as inputs grow") is therefore refuted for this implementation; the bottleneck is control flow.

linear and matmul: core-bound on a dependency chain. Both spend ~51–65 % of slots retiring and ~35–48 % in Backend Bound, which level 2 attributes almost entirely to Core Bound (Memory Bound ≤ 1.6 % even when the 64 MB weight matrix of linear 4096² must stream from DRAM on every call). The cost per multiply-accumulate is flat at 3.0–3.1 ns across a 256× change in data size, which is the signature of a latency chain rather than a memory limit: every iteration adds into the same sum, and at -O0 that accumulator also round-trips through a stack slot, so iterations cannot overlap and few execution ports are busy per cycle. Memory accesses are independent of this chain, so the out-of-order core overlaps them with it: the 64 MB weight stream needs only ≈1.3 GB/s. Naive matmul walks B down a column (a 4 KB stride at N = 1024: a new cache line, and nearly always a new page, every access); this is visible only as a small rise in Backend Bound (34.6 → 42.2 %) and per-MAC time (+11 %) at 1024³, not as the dominant Memory Bound (84 %) reported for the same textbook loop in the ISPASS'14 matrix-multiply case study, where a much faster inner loop exposes the column-stride misses.

conv: highest Retiring, but on overhead. Convolution retires 60–71 % of slots with zero Memory Bound: its inputs are small and reused 9–75 times per output, so they stay in L1/L2. High Retiring here does not mean efficient: at 4.7–6.3 ns per MAC it is slower than matmul, because every image[c][i+ki][j+kj] and kernel[f][c][ki][kj] access at -O0 dereferences 3–4 pointer levels; most retired uops are address arithmetic and loads (level 2: 58–69 % "light operations"). Bad Speculation falls from 12.9 % to 5.9 % to 2.8 % as the work per output grows from 9 to 27 to 75 MACs: the data-dependent ReLU branch runs once per output, so its mispredictions are amortised over more arithmetic. Core Bound stays ≈24–25 % (the same accumulator chain as above).

softmax: compute-bound on the math library. 56–66 % Retiring and 29–33 % Core Bound come mostly from the expf() call per element (and the extra logf and three passes over the data). Branch prediction is excellent (≤ 1.2 %) because the running-max comparison is rarely true. It is the one kernel whose Memory Bound clearly grows with size: 2–2.5 % → 7.0 % at 10⁷ elements (80 MB), where its three passes no longer fit in the 30 MB L3, and Frontend Bound also rises (3 → 7 %).

Compute vs. memory as inputs grow. Across all kernels, Memory Bound grows with size only slightly (≤ 7 %) because the unoptimised kernels consume data far more slowly (0.7–1.6 GB/s) than one core can stream it. Arithmetic intensity predicts what changes once the compute is optimised: relu, softmax and linear perform O(1) operations per value loaded (each weight of linear is used exactly once), so after removing the branch and the dependency chains they should become memory-bandwidth bound at large sizes. Matmul and convolution reuse each value O(N) or O(K²·F) times, so they should stay compute-bound, provided the access pattern is cache-friendly (blocking/tiling); naive matmul at 1024³ is the first that would turn memory-bound.

6. Issues and debugging

  • Primer vs. code. The primer describes plain softmax and linear weights as W[i][j] without bias, but the provided tests require log-softmax and W[out][in] + bias. I treated the provided tests as the specification.
  • Test helpers. init_image/init_kernel only accept 5×5 and 1×3×3 arrays, so the handout's 2-channel example could not be expressed with them; I wrote shape-generic helpers. The provided test_conv cleanup passes kernelSize where it means the output size; it works only because both are 3.
  • Profiling node. The login node is a Cascade Lake Xeon (Gold 6252N), so --force-cpu spr would mislabel its counters; all profiling was run on the Sapphire Rapids ece5755 partition, and each run was kept well under its 5-minute job limit.
  • Hidden branch behaviour. An early harness using the in-place applyRelu() would have made all inputs non-negative after the first iteration, hiding the mispredictions that dominate relu; the harness now preserves the input.
  • Tooling. The cluster lacks matplotlib/pip, so the charts are generated as SVG with Python's standard library (perf/plot.py).

7. Ideas for improving performance (from the Top-down data)

  • relu (Bad Speculation 60 %): make it branchless (fmaxf(x, 0), or -O2, which emits maxss/maxps), then vectorise (AVX-512: 16 floats per instruction). It should then become memory-bound at 10⁷.
  • linear / matmul / conv (Core Bound 24–47 %): keep the accumulator in a register (-O2) and break the single dependency chain with several independent accumulators or SIMD lanes; for matmul, interchange to i-k-j so B is read along rows (unit stride) and tile for L1/L2.
  • Data layout (conv's address-arithmetic Retiring): store tensors contiguously instead of as pointer-to-pointer arrays to remove the 3–4 dependent pointer loads per element; then lower convolution to matmul (im2col), as planned for later labs.
  • softmax (Core Bound on expf): fuse the max and exp passes, vectorise exp, and reduce passes over memory, which matters once it becomes memory-bound at 10⁷.
