ECE5755 / CS5754 Lab 3: Sparse Matrix Multiplication and im2col

Pablo Penalba (pp555) · Fall 2026

1. Implementation

  • matmul_sparse() has the same interface as matmul and returns NULL when A_cols ≠ B_rows. Part 1 (csr_from_dense) converts A to CSR in two passes: the first counts the nonzeros of each row into the cumulative row_ptr array (length A_rows + 1, row_ptr[0] = 0), and the second copies each nonzero into values and its column into col_idx, row by row with columns ascending. Part 2 (csr_matmul) computes each row of C as the sum of the nonzeros A[i][k] times row k of B: for each stored nonzero the value is held in a register and the innermost loop adds a · B[k][j] into C[i][j] with unit stride over both rows. Only stored nonzeros are visited, so part 2 does nnz × N multiply-adds (MACs) instead of N³. Nonzeros are visited in ascending k, so each element of C adds the same terms in the same order as matmul, minus the zero terms, and the results are identical. The two parts are separate functions (with csr_free) called by matmul_sparse, so the profiling driver can build the CSR once and loop over part 2 only.
  • im2col() builds a (C·k·k) × (out·out) matrix: row (c, ki, kj) holds, for every output position, the input pixel that kernel weight multiplies (any stride, no padding). col2im() reshapes each row of the F × (out·out) product back into an out × out feature map. convolution_im2col() flattens the kernels over all channels in the same (c, ki, kj) order (the provided kernel_flatten reads only channel 0), multiplies the F × (C·k·k) kernels by the im2col matrix with matmul or matmul_sparse (selected by MatmulType), reshapes with col2im, adds the bias, applies ReLU and frees every intermediate.

Testing. All 33 unit tests pass (make all_tests). Every hand-checked matmul case also runs through matmul_sparse. Further tests check the CSR arrays of the handout's example matrix against the values given there (row_ptr = {0, 2, 4, 7, 8}, …) and its product, all-zero rows and an all-zero matrix (nnz = 0), incompatible shapes, and random non-square inputs at 0, 1, 10, 50 and 100 % density against matmul, with non-integer values to confirm the identical summation order. Every convolution test runs the direct, im2col + matmul and im2col + matmul_sparse paths.

2. Profiling methodology

Inputs. perf/profile.c generates N × N matrices once with a fixed seed. Each entry of A is uniform in [−1, 1] and is kept with probability d, the density (fraction of nonzeros; sparsity = 1 − d); B is dense. Both kernels therefore see identical inputs, and a checksum of the outputs confirms they agree. N = 128, 512 and 1536 bracket the cache hierarchy of the profiling node (48 KB L1d, 2 MB L2 per core, 30 MB L3): A + B + C occupy 192 KB (in L2), 3 MB (beyond L2) and 27 MB (about the L3 size). Densities are 1 % and 10 % (high sparsity) and 50 % and 100 % (low sparsity): 24 (kernel, N, d) inputs in all.

Looping only the function under test. For matmul the timed loop calls the whole kernel. For matmul_sparse the CSR is built once before the loop (its time is reported separately) and only part 2, csr_matmul, is looped. Iteration counts are set per input so the loop runs 5.6–12.4 s. Setup and teardown (generating the inputs, building the CSR, freeing) take at most 0.26 s (real minus loop time), ≤ 3.2 % of any run, and an iters = 0 run of every input profiles setup alone: its profile is very different (23–26 % Frontend Bound at N = 128, up to 16 % Bad Speculation at 50 % density), so without the loop it would distort the results.

Measurement. Every run is a separate SLURM job on the Sapphire Rapids ece5755 node (Xeon Silver 4514Y; SMT disabled). The node is shared, so perf/on_core.sh pins the program to the core SLURM assigned to the job and passes that core to toplev, which counts only that core: toplev.py -l1|-l2 -v --no-desc --force-cpu spr --core S<s>-C<c>. For each input perf/run_toplev.sh runs the program uninstrumented under time -p (the real time is reported), then under toplev at level 1 and at level 2, then the setup-only run; perf/summarize.py collects the results. All 72 profiled runs report MUX = 100 % (no counter multiplexing). The three independent measurements of the time per call (the timed run and the two toplev runs) agree within 1 % for 18 of the 24 inputs; the other six (sparse, N ≥ 512) differ by 2–11 %, with the uninstrumented run slowest in four of them, which I attribute to other jobs sharing the L3 and memory bandwidth.

4. Analysis

matmul ignores sparsity. For each N, the four densities run within 0.2 % of each other and have the same Top-down profile (Figure 1). A floating-point multiply by zero has the same latency and throughput as any other, and the loop has no data-dependent branches, so zeros cost exactly as much as nonzeros. Its bottleneck is the one found in Labs 1 and 2: every iteration adds into the same sum, which at -O0 is also stored and reloaded through the stack, so iterations form one serial dependency chain and 35–41 % of slots are Core Bound. The cost per MAC grows from 3.08 to 3.36 ns as the working set leaves L2 and then fills L3: the inner loop walks B down a column, touching a new cache line per access, and at N = 1536 a column (96 KB of lines) no longer fits in L1d. Memory Bound is still only 1.6 %, because these loads do not depend on the chain and are issued early; their latency appears as a longer chain wait (Core Bound 35 → 41 %).

Sparse work scales with nnz, so speedup tracks sparsity. At N = 1536 the time per call grows 1 : 10.5 : 56 : 115 from 1 % to 100 % density, close to the 1 : 10 : 50 : 100 ratio of nnz. The speedup over matmul is therefore about (1 / d) × (naive cost per MAC ÷ sparse cost per MAC): 90–173× at 1 %, 10–16× at 10 %, 2–3× at 50 %. Skipping the zeros is by far the largest effect, but the CSR kernel is also cheaper per MAC, which is why it is still 1.42–1.50× faster at 100 % density for N ≥ 512.

Why each sparse MAC is cheaper. The CSR loop is in i-k-j order: one nonzero A[i][k] stays in a register while the inner loop updates C[i][j] from B[k][j]. Consecutive iterations write different elements of C, so there is no loop-carried floating-point chain and the out-of-order core overlaps them. At N ≥ 512 Core Bound falls from 37–41 % (naive) to 14–25 %, and Retiring rises from 57–62 % to 68–80 %. The loop also does less work per MAC: time per MAC × Retiring, which is proportional to µops retired per MAC, is ≈ 1.2× lower than naive at every size (1.55–1.62 against 1.92–1.95 ns·Retiring at 100 % density), because the row pointers and a are hoisted out of the inner loop instead of being reloaded through the stack each iteration. The CSR indirection itself (loading values[p], col_idx[p] and the row pointer B[col_idx[p]]) happens once per nonzero and is amortised over N inner iterations. Memory Bound stays ≤ 2.7 % for every sparse input: col_idx selects the rows of B in a data-dependent order, but each selected row is then streamed contiguously, so the hardware prefetchers still work. Bad Speculation (≤ 4.8 %) and Frontend Bound (≤ 3.9 %) rise slightly at 1 % density, where rows of A hold only 1.3 nonzeros on average at N = 128 and the trip count of the loop over nonzeros is short and irregular.

Row length, not density, sets the cost per MAC. The sparse cost per MAC is 3.14–3.40 ns at N = 128, 2.13–2.40 ns at N = 512 and 1.93–2.24 ns at N = 1536. At N = 128 the CSR kernel loses its per-MAC advantage, and at 100 % density it is 2 % slower than matmul. It does not retire more µops per MAC (1.57, against 1.55 at N = 512); instead Core Bound rises to 40–44 % and Retiring falls to 50 %. The extra time is stall cycles, not extra work. What changes with N is the length of each pass of the inner loop (N iterations per nonzero): at N = 128 a pass is 12× shorter than at N = 1536. I did not isolate the cause (level 3 is multiplexed on this node, see Lab 2), but the likely explanation is the pass boundary. At -O0 the loop counter j is stored and reloaded every iteration, a serial chain that restarts for every pass, and each pass ends with a loop exit (Bad Speculation is 2.8–4.8 % at N = 128 against ≤ 2 % at N = 1536). With short passes these boundaries are frequent enough to keep the core from overlapping consecutive passes. Per-call fixed costs are not the explanation: a linear fit of the N = 128 runs at 10 % and 50 % gives ≈ 7 µs per call (allocating and zeroing C, the row loop) plus 3.14 ns per MAC, which predicts the 1 % run within 2 % (73.5 against 72.1 µs).

Cost of building the CSR. Part 1 is two O(N²) passes over A: 10.5–51 ms at N = 1536, against 12.2 s for one naive multiplication, so even with the build included matmul_sparse wins at every input with N ≥ 512. In a network the weights would be converted once and reused. The build is slowest at 50 % density at every size (402 µs, 5.66 ms, 51 ms). There the A[i][k] != 0 test is random and the branch predictor is wrong about half the time, while at 1 % and 100 % it is almost always predicted correctly. The setup-only profiles of matmul_sparse at N ≥ 512 show this: Bad Speculation is 15.8 % at 50 % density against 1–6 % at the other densities (the input generator's own density test contributes too, since matmul's setup at 50 % shows 5–7 %).

5. Issues and debugging

  • Looping only part 2. The handout requires that only the CSR multiplication be looped, while matmul_sparse must keep matmul's interface. Splitting it into csr_from_dense, csr_matmul and csr_free (declared in matrix_ops.h) keeps both: matmul_sparse calls all three, and the profiler calls part 1 once and loops part 2.
  • Exact agreement with matmul. Floating-point addition is not associative, so a different summation order could have caused rounding differences in the comparison tests. Visiting nonzeros in ascending column order makes the CSR loop add the same terms in the same order, so the random tests compare non-integer values at the 10−6 tolerance.
  • Checksum mismatch that was not a bug. The driver's checksum summed one output element over every call, so it differed between the kernels, which run different numbers of calls. Divided by the call count it is the same for both (e.g. 1.806 at N = 128, 10 %).
  • Iteration sizing. I estimated the iteration counts from the Lab 2 cost of the i-k-j loop (≈ 1.8 ns per MAC). At N = 128 the sparse kernel costs 3.1–3.4 ns per MAC (Section 4), so those runs took 8–10 s instead of 6 s, still well inside the 5-minute job limit.
  • Shared profiling node. As in Lab 2, other users' jobs share the ece5755 node, so a hard-coded taskset -c 0 / --core S0-C0 (as in the template Makefile) can fail or profile the wrong core. Each job pins to its assigned core and passes that core to toplev. Neighbours still share the L3 and memory bandwidth, which explains the 2–11 % spread of six sparse inputs. Because of time, each input was profiled once per level rather than averaged over several trials.
