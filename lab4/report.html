1. Implementation

matmul_thread() has the same interface as matmul and returns NULL when A_cols ≠ B_rows. It partitions the output matrix: the A_rows rows of C are split into T contiguous blocks (block sizes differ by at most one row, the first A_rows mod T blocks taking the extra row), and one POSIX thread is created per block with pthread_create. Each thread receives a small argument struct (A, B, C, its [row_start, row_end), and the dimensions) and runs the same i-j-k loop as the Lab 1 matmul over its own rows; the main thread then pthread_joins all of them and returns C. A and B are only read, and every element of C is written by exactly one thread, so no locks or other synchronization are needed. Each output element sums the same terms in the same order as matmul, so the results are bit-identical. T = 8 (the cores a Slurm job is given) by default, clamped to A_rows so no thread is idle; the environment variable MATMUL_THREADS overrides it, which the profiling scripts use for the 1/2/4/8-thread sweep.

False sharing. Partitioning by whole rows already keeps threads on separate elements, but two rows could still share a 64-byte line where one row's end meets the next row's start. Each row of C is therefore allocated with posix_memalign on a 64-byte boundary and padded to a whole number of cache lines, so no cache line ever holds data from two rows, and hence from two threads. The rows remain ordinary heap blocks that the caller frees with free(), exactly like matmul's.

Testing. All 31 unit tests pass (make all_tests). Every hand-checked matmul case (square, non-square, identity, dot and outer products, incompatible shapes) also runs through matmul_thread. Further tests compare matmul_thread with matmul on random non-integer inputs at 10−6 tolerance over shapes chosen to stress the partitioning (1, 3, 37, 100 and 129 rows, rows of C shorter than a cache line and not a multiple of one) with 1, 2, 3, 7, 8 and 64 threads, including more threads than rows. The im2col convolution tests run with both MATMUL_BASE and MATMUL_THREAD.

2. Profiling process

Program under test. perf/profile.c generates two N × N matrices once with a fixed seed (uniform in [−1, 1]), then calls matmul or matmul_thread in a loop, freeing each result, and prints the loop time per call and a checksum. Both kernels see identical inputs; the checksum per call is the same for every variant at each N. The iteration count is set per input so the loop runs 5.6–13.6 s; setup and teardown (time's real minus the loop time) take at most 0.12 s, ≤ 2 % of any run, so the function under test dominates. Sizes N = 256, 512, 1024 and 1536 bracket the cache hierarchy of the profiling node (48 KB L1d and 2 MB L2 per core, 30 MB shared L3): A + B + C occupy 0.75 MB, 3 MB, 12 MB and 27 MB. Each size is run with the Lab 1 matmul and with matmul_thread at 1, 2, 4 and 8 threads: 20 inputs. Everything is built with the provided Makefile flags (-O0 -lpthread).

Profiling only the cores in use. Every run is a separate Slurm job on the Sapphire Rapids ece5755 node (Xeon Silver 4514Y), requested with srun -p ece5755 -c 8; the job received CPUs 0, 2, …, 14, which are 8 distinct physical cores. perf/on_core.sh reads the job's allowed CPUs, picks T of them on distinct physical cores (one per thread; 1 for matmul), runs the program under taskset -c <those CPUs> so the threads cannot migrate elsewhere, and maps each CPU to its toplev core name from /sys/devices/system/cpu/cpuN/topology. toplev then counts exactly those cores: toplev.py -l1|-l2 -v --no-desc --force-cpu spr --core S0-C0,S0-C10,… taskset -c 0,2,… ./perf/profile matmul_thread N iters. With several cores in --core, toplev reports each metric over all their slots, i.e. the mean core. Cores are never hard-coded, since the node is shared with other students' jobs. For each input perf/run_toplev.sh runs the program uninstrumented under time -p (whose real time is reported), then under toplev at level 1 and at level 2; perf/summarize.py collects the results. All 40 profiled runs report MUX = 100 % (no counter multiplexing). The three independent timings of each input agree within 1 % except at N = 1536 with 2 and 4 threads (4–8 %), which I attribute to other jobs sharing the L3 and memory bandwidth.

4. Analysis

Threads scale almost perfectly. Relative to matmul_thread on one thread, 2, 4 and 8 threads are 1.99–2.00×, 3.95–4.00× and 7.65–7.98× faster (only N = 1536 at 2 threads, at 1.93×, falls in the noisy range noted in Section 2), and at every size the work per core (core·ns/MAC, Table 1) stays within 5 % of the one-thread value. Figure 1 shows why: for a given N, the per-core Top-down profile is the same at 1, 2, 4 and 8 threads to within about 1 % of slots. Adding cores does not change how each core runs, because the threads share nothing they write. Each core is still limited by the bottleneck found in Labs 1–3: at -O0 every iteration adds into the same sum (stored and reloaded through the stack), a serial dependency chain that leaves 30–41 % of slots Core Bound. Multithreading does not shorten that chain; it runs 8 independent copies of it, one per core, which is why the speedup is close to the core count.

No coherence or bandwidth penalty. The architectural risks of sharing data across cores do not appear in the counters. Machine Clears, where memory-ordering conflicts between cores (false or true sharing of written lines) are counted, are ≤ 0.4 % of slots at every thread count: each cache line of C belongs to a single thread (Section 1), and A and B are only read, so their lines stay in the Shared state in every core's caches and generate no invalidations. Memory Bound stays ≤ 3.1 %. The inner loop walks one column of B (one new 64-byte line per iteration), but consecutive j reuse the same lines, and a column's lines (N × 64 B = 96 KB at N = 1536) fit in each core's private 2 MB L2, so even with 8 cores streaming the whole of B, almost every load is served by a private cache and the shared L3 and DRAM bandwidth is not a limit. The fixed per-call serial work (creating and joining the threads, allocating C in the main thread) is small: fitting T(p) = s + W/p to the 1- and 8-thread times gives s ≈ 0.34 ms at N = 256 and 512. That is 5 % of the 6.8 ms 8-thread call at N = 256 (Amdahl's law: the reason 8-thread scaling there is 7.65×, not 7.96× as at N ≥ 512) and negligible for larger N, where the work grows as N³.

Differences between input sizes. The cost per MAC rises with N for both kernels (matmul: 3.07, 3.11, 3.34, 3.35 ns), together with Core Bound (35.5 → 41 %) and a small Memory Bound share (0 → 1.2 %) once N ≥ 1024. A + B + C fit in L2 at N = 256 but exceed it from N = 512, and at N ≥ 1024 the column of B touched for one j (64–96 KB of lines) no longer fits the 48 KB L1d, so most B loads come from L2. These loads do not depend on the sum chain and are issued early, so their extra latency shows up mostly as more stall cycles at the chain (Core Bound) rather than as Memory Bound, the same pattern as in Lab 3.

Why one thread is slower than matmul. All the efficiency lost against the Lab 1 baseline (0.86–0.98) comes from the single-thread cost, which is 1.5–1.6 % higher than matmul at N ≤ 512 and 8–12 % higher at N ≥ 1024; scaling from there is near-ideal. Time × Retiring, which is proportional to the µops retired, is 1.10× that of matmul at every N: the worker executes 10 % more µops per MAC. The loop is the same, but at -O0 the worker reads A, B and A_cols through the argument struct (w->A[i][k], w->B[k][j], k < w->A_cols), which costs one extra load of w per access compared with matmul's locals. At N ≤ 512 those loads fill issue slots that were idle waiting on the sum chain: Core Bound falls by 5–6 points, Retiring rises by the same amount, and the time barely changes. At N ≥ 1024 the slots are not free: the extra loads lengthen the address chain of each B load, which now misses L1, so they add time. Copying the struct fields into local variables at the top of the worker would remove this overhead, making each access as cheap as in matmul; I found it only after profiling and kept the submitted code identical to what was measured.

5. Issues and debugging

  • I is a macro. The template's matrix_ops.h includes cblas.h, which includes <complex.h>, where I is the imaginary unit. My identity-matrix test variable named I failed to compile with "incompatible type … complex float"; renaming it fixed it.
  • Profiling several cores. The Lab 3 script pinned to the first CPU of the job and passed one core to toplev. With 8 threads it must pin to as many CPUs as threads, on distinct physical cores (two threads on SMT siblings would share one pipeline), and list all of them in --core. The 2- and 4-thread runs use only 2 or 4 of the job's 8 CPUs, so idle cores are not averaged into their profiles. A test run showed that toplev prints one aggregate line per metric for the listed cores, and that the job's 8 CPUs map to 8 different core ids, so every thread had its own core.
  • Checksum mismatch that was not a bug. The driver adds one output element per call to its checksum, so variants with different call counts print different checksums; divided by the call count they agree for every input, which the summary script now checks.
  • Shared node and dropped connection. The batch ran under nohup and survived my SSH session dropping midway; the script skips finished runs, so it can be restarted. Other users' jobs share the L3 and memory, which explains the 4–8 % spread at N = 1536 with 2 and 4 threads. Each input was profiled once per level because of time.
